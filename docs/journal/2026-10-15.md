## Slice153 - O4 frame pacing (candidate, not owner-measured)

Branch `codex/optimization-plan-151`, base `b963112`. Build
`private/slice153-pacing-build/build`, launcher `--mode pacing`, pins in
[slice153-pacing.json](../inputs/slice153-pacing.json) and
[slice153-pacing-runtime.json](../inputs/slice153-pacing-runtime.json).

Diagnosis carried over from slice152 (Hypothesis, now testable): audio was the only
wall-clock throttle, and `wait_for` blocked on 4 x 512-frame buffers (10.67 ms) against
16.67 ms guest frames. The new mode removes that quantization instead of tuning it.

Design (files: `native/pacing.hpp/.cpp`, `native/frame_clock.hpp/.cpp`, `native/host_io.*`,
`native/window.cpp`, `native/native_vulkan.cpp`, `native/perf_probe.*`):

- Clock: QueryPerformanceCounter. Waits use a high-resolution waitable timer, with
  a 0.5 ms spin for the final stretch and a 1 ms `Sleep` fallback.
- Grid: 60 Hz, kept exact by storing the deadline scaled by the rate. The donor's
  `frame_cycles` is `kEeClock / 60`, so 60.000 Hz, not 59.94. Running 59.94 Hz would
  make the guest 0.1 % slow, which contradicts the 100 % speed target.
- Late frames are counted and continue. A frame more than one period late restarts the grid
  one period after the late release, so no guest frame is replayed and the clock is not raised.
- Audio (paced): no waits. Frames are resampled into a 16384-frame ring. 16 x 256-frame
  WinMM buffers are submitted only while the device holds at most 2816 frames. Start waits
  for 2880 frames. The PI controller (P 0.03, I 0.002 per second, anti-windup) moves the
  ratio within +-0.5 %, with a time constant near 2 s.
- Diagnostics: VBlank interval histogram (10 buckets, 12-35 ms), queue min/median/max,
  resample ratio, late frames, underruns, ring overflow. Printed by F8 and the periodic
  report under `GT4_PERF=1`. The histogram also runs under `GT4_PACING=audio`.
- Presentation: FIFO stays the default. `GT4_PRESENT_MODE` accepts fifo, mailbox and
  immediate, refuses unknown names, and checks surface support at swapchain creation.

Evidence (all on this build):

- `pacing_fixture`: parsers, exact grid over 10,000 frames, late and stall handling, unity
  resampler bit-identical, 1 kHz sine within linear-interpolation bound, controller
  convergence to 2e-4 of a 0.2 % drift, saturation at 0.5 %, no underrun under 1 % jitter,
  ring wrap, histogram buckets, sample windows, report format. PASS.
- `host_io_fixture`: existing blocking-device checks unchanged; new paced device run for
  3 s at 60 Hz: worst push 0.02 ms (never waits), underruns 0, device consumption at wall
  rate (139,520 frames completed), ratio bounded. PASS.
- Start-up transient, measured with a per-frame trace (removed afterwards): the device begins
  consuming about two guest frames after first submission, so the queue peaks near 4,500
  frames (about 95 ms) and falls toward the 2880 target at roughly 4 frames per guest frame
  (about 8 s). The ratio stays at the -0.5 % bound during that time. No underrun. Not
  corrected; see limits.
- Headless 4200 frames, 12-press schedule: 42 frame dumps identical between the slice152
  async build and this build.
- CTest 18/18; Python 217 OK (one pre-existing skip) with `GT4_NATIVE_BUILD` on this build.
- `GT4_PRESENT_MODE=mailbox` forwarded, logged by the host, and recorded in `result.json`.

Not done: no window or gameplay session was started by the implementing agent. Frame
median, p95, p99 and speed are owner measurements. Whether a 60 Hz monitor aligns with
the grid under FIFO is unknown until the owner runs it.

Limits and decisions to review:

1. The start-up transient above exceeds the 60 ms target for several seconds. Options are a
   lower start threshold, a device-latency estimate, or a wider authority. The owner's
   ±0.5 % bound was kept.
2. FIFO against a 59.94 Hz panel can add present stalls. `GT4_PRESENT_MODE=mailbox` is the
   experiment.
3. Paced shutdown drops the ring remainder (under 60 ms).

    $env:GT4_PRESENT_MODE=mailbox   (experiment only; FIFO is the default)

Crash triage (read-only, scripts in private/slice153-crash-triage): the halt is

registers: sp 0x01FFF5C0, fp 0x00640000, gp 0x006DDDF0, a0 0xFFFFFFFF, ra

dispatcher halts where it is consumed, not where it was written. Immediately
before the halt the log has the session's only unmapped memory accesses: reads

the cause is Unknown). Next: reproduce in the slice114 baseline to separate a
regression from a pre-existing bug, and add env-gated return-target validation
plus a stack dump at halt.

License crash follow-up: with every slice 151-153 optimization disabled in the
same executable (GT4_PACING=audio, GT4_GS_SYNC=1, PS2_VU_INTERPRET=1; session
021509), opening the first license test also halted, after 961 frames, with
"no translated code at 0x00000000 (ra 0x00000000)". **Confirmed:** the crash is
not caused by the VU1 AOT, async GS or pacing changes. The halted thread's stack
(decomp names) runs RaceLicense virtual 95 → RaceSolitaire::loadDemoInputs →
AutomobileControlRecord::Manager::load. The earlier crash also had r1 = 0xE48C,
the offset loadDemoInputs adds to its object. Manager::load reads a record count
from the license's demo-input data and loops over that many records; a garbage
count would overrun memory. **Hypothesis:** the license demo-input data is not
loaded (or is loaded wrong/late) before loadDemoInputs runs, pointing at file
loading, decompression or load timing in the runtime models.

License data trace (read-only, private/slice153-license-trace): entries are
loadDemoInputs 0x3EAD18 and Manager::load 0x346BB8 (232 bytes); the halt pc lay
in func_00346CA0's unaligned LDL/LDR copy path. GT4.VOL holds 592
`replay/license/*` PS2ZIP files; decoded, each is a Serialize::Base container
whose first word is 0x40, so Manager::load cannot be reading the raw decoded
file directly (64 records x 5,364 bytes would overrun a ~15 KB buffer). No CDVD
read is traced in these logs (the donor trace needs `--trace-iop-hle`). Ranked
hypotheses: wrong/stale buffer contents at arg1+0x1AA4; uninitialized RAM;
an EE translation error in LDL/LDR; decompression or timing (low). Next:
env-gated logging at loadDemoInputs/Manager::load entry and in the PS2ZIP
loader for `replay/license/` names, plus an LDL/LDR semantics check.

Unaligned access check (private/slice153-ldl-check): the donor LDL/LDR/SDL/SDR/
LWL/LWR/SWL/SWR helpers and the generated copy loop of func_00346CA0 match a
byte-wise little-endian reference for every alignment (24,064 checks, 0
failures, including all 64 source/destination alignments of the 5,364-byte
copy). **Refuted** as the license-crash cause. Side finding: a lone LWR with
offset != 0 writes only the low 32 bits instead of sign-extending to 64 bits
(MIPS III); masked when paired with LWL as here. Backlog: fix and scan for
lone LWR uses.

## Slice154 - O1 follow-up: per-program VU1 flag elision (candidate, not owner-measured)

Branch `codex/optimization-plan-151`. The working tree was built on `8b0101b`; three docs commits
(`d0d8992`, `150f626`, `8b0101b`) landed on the branch during the session and are not part of this
change. Nothing is committed or staged. Build `private/slice154-vu1-flags-build/build`, launcher
`--mode vu1-flags`, pins [slice154-vu1-flags.json](../inputs/slice154-vu1-flags.json) and
[slice154-vu1-flags-runtime.json](../inputs/slice154-vu1-flags-runtime.json). Details: [BUILD](../BUILD.md).

Analysis (emitter `tools/vu_recomp/src/vurecomp.cpp`, contract `vu_recomp_contract.hpp`):

1. Decision: the old liveness pass was not used. Its `kills` rule ignored the FlagPipe window
   (a write is visible to a reader four instructions later, not one), and in practice every
   GT4 image has a MAC reader (0x1A at 12 sites), so `image_flags_used` made every program
   keep everything. It is replaced by an observation walk per write: a successor-state search over
   the program's CFG with states "no later write yet" and "distance since the first later write"
   (windows 4 for MAC, 3 for clip). A reader sees the write unless a later write is at least the
   window before it. An exit observes the write when no later write of the channel precedes it.
2. Exits are the E bit (after the delay slot), lower-op fallbacks, unreachable successors, the
   jump-register dispatch, and every backward transfer (the budget charge may leave there).
   Exit state is exact: `r.mac` and `r.clip` are written back at every `VUGEN_SYNC`.
3. Donor facts used (read, not copied): `FlagPipe::mac_slot` (`mac_ts + 4 <= t`), `clip()`
   (`clip_ts + 3 <= t`), `flags()` (MAC from destination lanes; status chains through `r.status`),
   `clip_value` (chains through `r.clip`), the interpreter's `set_flags` on dest-zero ops (MAC 0),
   and `cop.cpp` `cfc2` (VU0 registers only; VU1 flags are unobservable to the EE).
4. Decision: status is not kept when the image has no status instruction. The corpus image (16 KiB,
   86 identical snapshots) has 0x12, 0x1A and 0x1C only; no 0x14-0x17 and no FSSET (0x15). Identity
   bit `image_status_used` is in the program digest and in the table row.
5. Decision: clip values are always computed (chain), only FlagPipe pushes are elided. A first
   version elided the clip computation and the fixture differential caught it (the VI results of
   0x1C readers differed). This is the reason for the chain rule in `clip_result`.
6. Decision: MAC for a write is computed only when a reader pushes it or it is the last write
   before an exit. The FlagPipe ring is unchanged for the readers, which see the same values by
   construction (a write no reader can see is never pushed).
7. Refusal added: an end bit in a branch or jump delay slot. The donor runs the target once more
   and then ends; the emitted code would continue. The corpus has none (0 refused); fixture added.

Findings during the work (all fixed here, all covered by a fixture):

- Destination-zero flag ops set MAC to 0 in the donor interpreter; the emitter skipped them. Pre-existing.
- The clip chain (above).
- Backward exits from a write's own successors were missed by the walk (found by the budget
  benchmark: several corpus states ended with the MAC of the input state, not of the last write).
- An end bit on a delay slot (above). Pre-existing divergence, not present in the corpus.
- The first headless smoke and verify ran on a table generated before the clip-chain, destination-zero,
  backward-exit and delay-slot fixes; both were discarded and repeated on the final table, which
  is identical to the table in the build (`cmp`).

Measurements (Confirmed unless marked):

- Sites over the 100 corpus programs: flag-setting writes 6,024. Before: MAC computed and pushed
  at all 6,024 with status. After: MAC computed at 642 (170 pushed for readers, 472 for the exit
  state), status at 0. CLIP writes 607; chain value at 607, FlagPipe pushes 403 (was 607).
- Micro-benchmark `gt4_vu1_flag_bench` (`tools/vu_recomp/tests/vu1_flag_bench.cpp`, CTest does not
  run it): 200 seeded states, both tables from the same records (namespace `baseline` emitted with
  `--no-flag-elision`). 200 compared, 0 failures on status, resume PC, registers and VU1 memory;
  68 budget exits. Timed: the 68 states that exhaust the 4,000-instruction budget inside
  generated code. Two runs: baseline 9,972 / 10,044 ns per call, elided 4,681 / 4,674 ns per call
  (ratio 0.47). [Hypothesis] the showroom's VU1 time (16.2 ms per frame) would fall in the same
  proportion if its programs behave like these; not measured on gameplay.
- Corpus differential (`gt4_vu_corpus_differential`): 100 programs matched, 208 checks, 0 failures.
- Fixture differential: 907 checks, 0 failures, including a budget sweep from 1 to 60 on the
  flag loop with resumed interpreter comparison and two chained calls (`cross_program_mac`).
- Registry control: 100 of 100 entries, 500 checks, 0 failures.
- CTest 18/18 on the final tree. Python `unittest discover`: 217 tests OK, one pre-existing skip.
- Headless smoke, 4,200 frames, the slice153 schedule: 42 frame dumps identical to
  `private/slice153-smoke/headless-153.frames.sha256`.
- Headless verify, `GT4_VU1_VERIFY=1`, the same schedule: at the 20,000-call checkpoint
  `verified=4300 verify_mismatches=0`; the run ended before the next checkpoint, so the total
  verified count is not recorded. Its 42 frame dumps are identical to the smoke.

Test expectations changed, each for a fixture or mode added in this slice: the authored
fixture program count (7 to 22), the refused-program count (1 to 2), the Python list of AOT
manifests and the matched-mode probe list (`vu1-flags` added). No check was removed.

Limits and decisions to review:

1. Owner frame measurement is not taken; the showroom VU1 time is not claimed.
2. Status is not maintained for an image without status readers. The verify and differential
   comparisons exclude status only in that case (`image_status_used`), and the comment says so.
3. The FlagPipe history is not transferred on an interpreter hand-off or budget resume (known
   limit, unchanged). Exit MAC and clip are exact, so the only difference is inside the window
   after a resume.
4. Random register seeds reach the end of a VU1 program rarely. The benchmark uses the fixed
   budget as its workload, and only budget-exhausting states are timed.
5. A VU1 image uploaded at run time gets a different identity; a mismatch falls back to the
   interpreter (counted as `identity_rejects`).
