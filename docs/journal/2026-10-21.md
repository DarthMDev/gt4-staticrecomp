## TASK-075, launcher side: pads through SDL3 (TASK-019 branch)

- The launcher reads pads through SDL3 3.4.18, the version the game ships, instead of the WebView Web Gamepad API. The
  `sdl3` crate 0.20 (its `sdl3-sys` 0.7.2+SDL-3.4.18) links `SDL3.dll` dynamically. Packages: `SDL3-devel-3.4.18-VC.zip`
  (sha256 78d84602...) and `SDL3-3.4.18-win32-x64.zip` (sha256 75c2c0fc...), both checked against the GitHub asset digest,
  in `private/tooling/sdl3-3.4.18`. `launcher/crates/gt4l-platform/build.rs` reads `GT4_SDL3_ROOT` (a worktree has no
  `private/`, so it must be set) and copies the DLL next to the test and app binaries.
- Only the gamepad subsystem starts (`SDL_Init(0)`, then `SDL_INIT_GAMEPAD`, no video): the Tauri window and its loop are
  not touched. `gt4l-platform/src/sdl_pads.rs` is the reader; `gt4l-platform/src/pad.rs` holds the pure rules.
- Mapping (the same as the game): SOUTH is `xinput:A` (Cross), EAST `xinput:B` (Circle), WEST `xinput:X` (Square), NORTH
  `xinput:Y` (Triangle), LB/RB, LT/RT (pressure), stick clicks, BACK `xinput:Back` (Select), START `xinput:Start`, D-pad, and
  the four stick axes. The controls file keeps its names, so the bindings and the game's reader stay as they are.
- `gt4l-tauri/src/pad_service.rs`: one thread owns the reader. It emits `pad-status` on change, `pad-live` at about 60 Hz
  while a pad is connected and the window is shown (sources at 0..1, sticks at -1..1, y down), and `pad-nav` for
  `a b x y lb rb start` and the directions (`pad_nav.rs`: first press at once, repeat after 420 ms, then every 110 ms; left
  stick past 0.5). `capture_binding` asks the service for the next new press (a button held at the start does not count);
  `cancel_capture` and a pause answer it with "capture cancelled". `pad_status` returns the last status for a page that
  opens later. The tray sets the service inactive when it hides the window for a game, so no SDL work runs during play.
- "Controller 1 of N" is the lowest SDL joystick id among the connected pads (`pad::active_pad`).
- UI: `nav.js` takes `pad-nav` and the right stick from `pad-live` (no polling). `controls.js` reads `pad-live` and
  `pad-status`; `controls-model.js` takes the pad-live shape (`padLive` and `padSummary` are dev-mock helpers now).
  The dev mock (`ui/dev/mock-data.js`) turns its Gamepad-like objects into the same events.
- Keyboard view: the fixed layout (read only, several keys per chip): D-pad left A or Left, D-pad right D or Right,
  D-pad up Up or E, D-pad down Down, Cross W or Enter, Square S, Circle Space, Triangle Backspace or Esc. Nitro (Shift),
  gear up (R), gear down (F), look back (Q) and camera (C or Tab) have no DS2 button in the table yet: they are listed in
  the legend, "to confirm". Keyboard rebinding is off (a key in the rebind overlay only cancels; Rebind and Reset are
  disabled in that view).
- NSIS: `installer/gt4recomp.nsi` installs `SDL3.dll` beside GT4Recomp.exe (`/DSDL3_DLL=...`). `tauri.conf.json` has
  `bundle.active: false`, and a resource under `private/` would break builds from a worktree, so no bundle resource was added.
- Checks: `cargo test --workspace` green (gt4l-platform 10 pad tests, gt4l-tauri pad_nav 5 and pad_service 4, the command
  contract passes with `pad_status` on all four lists). nav-test 149 of 149; focus-check 90 of 90 (headless Edge).

- Real exe (scratch `GT4RECOMP_DATA_DIR`, WebView2 remote debugging): SDL started (log line "controller input: SDL3 gamepad

  CPU-dispatched Visual C++ library region; no BMI. The launcher's AVX2 check is therefore a policy, and the game has

  (the Vulkan-on-D3D12 compatibility layer, 1.2). The check ignores those and CPU rasterizers, and also requires the
  four instance extensions the game enables, including `VK_KHR_surface_maintenance1` (new in 2025 drivers: the main
  risk on older NVIDIA and Intel drivers).

  pre-TASK-076 keys (Z, X, A, S, 1, 2, Enter...). The launcher writes every input to `controls.toml` after a remap, so
