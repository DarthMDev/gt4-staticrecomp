# 2026-10-25

## TASK-116 step 0 (P0 gate): what gt4-gs really answers in Performance mode

The rc6 plan gates both changes on one question (TASKS.md, "rc6 plan after the step 1 studies", step 3): in Performance
mode (`HWDownloadMode = 2`, NoReadbacks) does the GS process answer the 2 KiB flare readback with the same bytes as
Accurate (so a local answer would be byte-identical), with zeros (so the flares would be gone), or with older real pixels
(so a local answer is one frame late)? The owner's fact of 2026-10-24 — the street-light glows SHOW on George V in
Performance mode — already ruled out zeros; this probe answers the rest from a log.

**Probe.** `GT4_GS_READBACK_LOG=1` (new test switch, `native/gs_stream/gs_readback_probe.*`) prints one line per READ_FIFO
reply with the frame, guest destination, qwords, status, EE wait, nonzero byte count, the first 16 bytes, an FNV-1a 64
hash of the whole reply and whether the reply repeated the previous one for the same destination; at exit it prints one
row per destination (calls, distinct replies, repeats, zero replies, nonzero byte range, statuses, mean and max wait,
first and last hash). It also prints the `HWDownloadMode` of the ini named by `GT4_GS_CONFIG`, so a log says which mode
produced it. The probe only reads the reply after the client copied it: no record changes. `game_main.cpp` gives the
client the guest RAM window (`ps2::g_ram`), so destinations are EE addresses; the client itself stays donor-free.
`scripts/frame_cost_headless.py` gained `--readback accurate|no-readbacks` (writes `HWDownloadMode` 0 or 2, recorded in
`conditions.json`).

**Runs** (headless, 1x, surfaceless, gt4-gs 1.2.1 `887f5bf9…`, probe build `45c8c8df…`, 97,387,520 bytes, slice298;
`O:\gt4recomp-scratch\slice298-runs\`):

| Run | VBlanks | Readbacks | Flare destination | qwords | Calls | Distinct | Repeated | Zero replies |
|---|---|---|---|---|---|---|---|---|
| night Accurate | 16,000 | 5,026 | `0x01bf6f40` | 128 | 4,998 | 2,161 | 2,599 | 0 |
| night Performance | 16,000 | 5,026 | `0x01bf6f40` | 128 | 4,998 | 139 | 4,717 | 0 |
| day Accurate | 16,000 | 292 | `0x01bf6f40` | 128 | 264 | 52 | 129 | 0 |
| day Performance | 16,000 | 292 | `0x01bf6f40` | 128 | 264 | 6 | 258 | 0 |
| menus Accurate | 4,200 | 0 | - | - | - | - | - | - |
| menus Performance | 4,200 | 0 | - | - | - | - | - | - |

- **The per-frame night readback is the flare table** (Confirmed): one 128-qword reply per race frame to `0x01bf6f40`
  (the flare object of `RacePS2Base+0xDA0`), in a day race only while the sun is sampled (264 of 16,000 frames).
  `128` qwords is unique among every readback measured, so it is a safe allow-list key.
- **Performance mode does NOT answer zeros** (Confirmed): the night reply has 27..2048 nonzero bytes, never zero, and
  the glow shows, as the owner reported. The status field is 0 in every reply, including the ones that are all zeros:
  gt4-gs 1.2.1 never sets `kReadbackZeroFilled`, so the client's zero-filled counter cannot detect a blank reply.
- **The Performance reply is stale, not identical** (Confirmed by the counts, High confidence for the mechanism): the
  same buffer is read without waiting for the GPU, so distinct replies fall from 2,161 to 139 and repeats rise from
  2,599 to 4,717 of 4,998. The visibility table the game sees is therefore a *previous* frame's, sometimes several
  frames old, depending on GPU timing.
- **Verdict for step 1:** the local answer is **one frame late, not byte-identical**. That is not a regression: it is
  exactly what Performance mode already delivers today, only deterministic (the previous frame's accurate reply,
  independent of GPU timing) and cheaper (no 5.5 ms VU1 drain, no round-trip wait).
- **What actually breaks in Performance mode** (Confirmed): the one-shot readbacks. Car icons: the 256-qword replies
  become a constant 1024-byte pattern and the 768-qword ones lose their content (first reply all zeros); the loading
  picture (2 x 26,880 qwords) comes back all zeros. This matches the launcher's claim about the icons and contradicts
  its claim about the flares.
- **EE waits of the flare reply** (1x, mean/max): night Accurate 0.911 / 12.829 ms, night Performance 0.462 / 4.208 ms;
  day Accurate 0.639 / 1.490, day Performance 0.276 / 0.997. The 5.5 ms VU1 drain is separate (`mtvu download`) and is
  what step 1 removes.
- **Identity:** the same build with `GT4_GS_STREAM_HASH=1` gives the release 1.3.0 night hash `c091716e3cb40d79`
  (27,259,715 records), equal to the slice278/279 pin in docs/BUILD.md: the probe posts nothing new.

**Launcher help text corrected** (en-US and pt-BR, and `docs/launcher/gs-settings.toml`): Performance Mode now says the
game stops waiting for the images, so the car icons can come out blank and the loading picture may be missing, while
night flares still show but can be a frame behind. The old text said flares were skipped.

**Checks:** CTest 46/46 in the probe build (new `native_gs_readback_probe`: ini section/case/comments/range, FNV-1a 64
vectors, aggregation, environment switch); Python suite 697 tests OK, 43 skipped (`GT4_NATIVE_BUILD` = slice298);
`tests/python/test_frame_cost.py` covers the new `--readback` mapping.
