Fork (GPL, PCSX2-tainted work, nothing near CoreGS 2.0):

- Dependencies for v2.8.2 were built fresh (`private/slice193-gt4gs-deps`): the nightly set of TASK-034 had other
  versions (FFmpeg 9.0.1, SDL 3.4.18, plutovg 1.3.3). Friction: the fork's script finds Visual Studio only with
  `vswhere -products *` on a Build Tools install (fixed in the script), and `cmd` mis-jumps `call :label` in an
  LF-only batch file (the local copy was converted to CRLF). FFmpeg is not needed to build or run the GS (bundled
  headers, loaded at run time): built with `BUILD_FFMPEG=0`, about 15 minutes.
- `pcsx2/GSStreamReplayer` executes the protocol records; `pcsx2-gt4gs` builds `gt4-gs.exe`; the MIT protocol files
  are vendored by SHA-256 (LF form, `eol=lf`, so the check holds on any checkout). PCSX2 builds without C++
  exceptions; the transport is in its own library with exceptions behind a no-throw adapter.
- Console output: PCSX2 writes its console with `WriteConsoleW`, which fails on a pipe; a fallback writes UTF-8 text,
  so `gt4-gs.exe` lines appear in the game's session log.
- Commits `0b51d4c3c` and `acf4f986e`; tag `gt4gs-v0.2.0-live` (prerelease from CI).

Main (MIT):

- `gs_stream_client`: `GT4_GS_PROCESS_SHA256` pin check (Windows CNG), `GT4_GS_CONFIG` -> `--config`,
  `WS_CLIPCHILDREN` on the game window at attach, message box when the GS process dies with a window attached.
  CTest scenarios for the pin and config added.
- Launcher `--mode pcsx2` with `--gs-scale N`; the probe verifies the package tree digest, sets the exe pin and
  writes a minimal `gt4-gs.ini` per session (headless: surfaceless and PNG dumps every 100 vsyncs).
- `tools/gs_live_check`: a producer with a never-shown parent window replays a capture into `gt4-gs.exe` and checks
  attach, resize, snapshot, shutdown and the kill path.

## TASK-037/038: readbacks, cache, window and crash handling (slice194)

Branches `task/037-038-gs-window` (main) and `gt4gs/window` (fork, commit `10851476b`, tag `gt4gs-v0.3.0`).

- Owner logs (TASK-036 at 3x): night race 213 late frames in 7,467; 1 readback per frame, 1.07 ms each; MTVU
  `gs_privileged` EE wait 3.38 ms/frame; stream 4.1 MB/frame (Nordschleife 4.8 MB/frame with 6 late frames). Cause:
  the per-frame readback makes the game wait for the whole GS pipeline, so GS-thread spikes (pipeline compiles at
  race start) land in the game frame. The headless readback replay reproduces the owner's mean (1.07 ms) and shows
  the cold-cache spikes (max 144 ms) that disappear with a warm cache (max 17 ms).
- Found: `gt4-gs.exe` 0.2.0 ignored `[Folders] Cache` and used `Documents\PCSX2` (cache, crash dumps), and opened a
  WASAPI audio stream (wrong SPU2 key). Fixed in 0.3.0.
- Found: the PCSX2 GS parses the GIF packets of all paths with one tag state; a packet injected inside another one
  crashed the GS thread in the first fixture version. The replayer now counts records that start inside another
  path's packet: 0 in every real stream so far.
- Found: DestroyWindow of the game window waits for a stalled GS window thread (994 ms in the stall fixture); in pcsx2
  mode WM_CLOSE now halts first and destroys the window after the GS process is gone.
- Readback modes: accurate (default) and unsynchronized (mean 0.11 ms, returns stale data: zeros for a drawn sprite).
- Checks: CTest 29/29, Python 350 OK, donor 42/42, pcsx2 41/41 = slice193 offline replay, kill test, stall, soak
  3,000 resizes, aspect check (same rectangles as TASK-009), readback check exact in accurate mode.
- Open: owner windowed test of slice194 (night race in both readback modes, Alt+Tab/fullscreen checklist).
