## TASK-017 phase 1: license demo FPU oracle (branch task/017-license-crash)

Goal: turn the cipher prototype into a repository oracle and find the bit-exact R5900 mul.s/div.s rule with the
game's own CRC as judge. Clean room: no PCSX2 or other GPL source was read; sources are prose and test data only.

Added:

- `scripts/license_demo_oracle.py`: reads the 592 `replay/license/*` demos through the pinned `gt4_volume` reader
  (in memory only), decrypts them like func_00579E00 with pluggable mul/div models and checks the game CRC.
  Tables are derived, not read from the ELF: FT[i] = 0x3F800000 + (2i+1)*0x4010 + (i>>5) (all 256 entries equal
  the ELF at 0x00655888, Confirmed), T8 = bit reversal (0x00655C90), standard CRC-32 table (0x00655358).
  `--search BEAM` runs a CRC-confirmed beam search that needs no division model: each step takes the chop quotient
  or one ulp above it; a path is accepted only when the full-file CRC matches the key.
- `tests/python/test_license_demo_oracle.py` (8 tests, about 5 s): table spot values, ps2autotests hardware
  vectors, a cipher round trip and model sensitivity, the saturation cycle, a synthetic search, and a disc test
  (skipped without the ISO) that checks all 592 first bytes and records that chop/chop fails the CRC.

Findings:

- Cipher facts (Confirmed): mul.s fs = FT[c], ft = state (0x00579EB8); div.s state = f1 / nb (0x00579EDC). The first
  plaintext byte equals key >> 24 for all 592 files under any model. The state saturates at 0x7FFFFFFF after
  about 250 steps (range 200-350), then follows the period-2 stream 0xFF/0x80, so only the first ~250 mul/div
  pairs of each file are tested. Plaintext starts with the body size (u32), "GT4M", then e.g. "RaceLicense".
- Whole-file CRC pass counts (all 592 files): chop/chop 0, chop/nearest 0, chop/srt2-cs-t3 0, booth-t8 with each
  div 0. Earlier prototypes: nearest/chop, nearest/nearest, IEEE with infinities, clamp at exponent 254: 0.
- Model-free ground truth (Confirmed by the game CRC): the beam search (C prototype in the scratchpad, beam 2000)
  found CRC-valid chains for 528 of 592 files; 487 files with a saturation step <= 400 were kept (the others are
  likely false matches and were excluded), giving 52,469 unique (dividend, divisor, quotient) div.s steps.
  On every one of them the hardware quotient is the chop quotient or one ulp above it, never anything else.
- div.s is not chop. Per-step agreement on the 52,469 steps: chop 60.9%, IEEE nearest 82.8%, idealized radix-4 SRT
  (digits -2..2, 13 digits, no correction) about 87-91%, radix-2 SRT with a carry-save residual and no final
  correction (`srt2-cs-t3`: 3-bit estimate, q=1 if y >= 2/8, q=0 if y >= -3/8) 93.1%, best variant found 94.1%
  (three-vector lookahead estimate). Reciprocal-times-dividend models: at most 80%.
- Structure of the hardware divider (High confidence): the result is floor or ceil of the exact quotient at
  2^-24 absolute (quotient in (0.5, 2)), so for q < 1 the uncertainty is one final ulp and for q >= 1 half an ulp.
  The choice depends on the low quotient bits (it prefers odd results, and runs of ones carry up), which is the
  signature of an uncorrected SRT digit recurrence with redundancy close to 1 (radix-2). An EM fit over the
  chains gives a zero-digit band of about |2w| < 0.34 with soft edges (Hypothesis: carry-save estimate error).
  The exact digit-selection and residual details were not identified.
- mul.s: ps2autotests (ISC, real PS2 output) give mul.s 1.0, 0x3FFFFFFF = 0x3FFFFFFE but 0x3FFFFFFF, 1.0 =
  0x3FFFFFFF. A radix-4 Booth array that recodes ft and drops partial-product bits below column T (1 <= T <= 22)
  reproduces both; exact chop does not. On the cipher data, Booth with T <= 12 equals chop on every step, so the
  demos cannot pin T. They also cannot separate mul from div errors, because only the stored div result is seen.
- div.s vector from the same suite: div.s 1.0, 0x3FFFFFFF = 0x3F000001 (chop gives 0x3F000000).

Not done / limits:

- No model passes all files, so no C++ function or runtime capsule was written and nothing changed in the build.
- The beam search in the repository script is Python (about 40 s per file at beam 600); the 4 s C prototype stays in
  the scratchpad. The confirmed chains are derived from game data and are not committed.

What would settle it: the exact divider recurrence (published EE/VU fDIV design notes, or more hardware vectors
for div.s on chosen operands), or further fitting of SRT variants against the 52,469 confirmed steps (the oracle
can regenerate them). A guarded game-specific fallback (retry the decrypt until the CRC passes) remains possible
but is not recommended.
