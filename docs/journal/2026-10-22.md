# Journal 2026-10-22 (TASK-027, CoreGS 2.0)

### Owner test 3 and the follow-up

- The owner saw the License Center 3D car at a locked 60 FPS and a Time Trial at 39-42 FPS, lower when driving into
  the sun. The window also showed the 16:9 picture squeezed into 4:3.
- Disk: about 10.7 GB of old local intermediates deleted from the worktree; the references the checks use are kept.
- The window now shows the full 16:9 picture (IN-356); a test checks the rectangle.
- The slowdown into the sun and at night came from the lens-flare readback: every time the game read back its small
  flare table, the renderer copied all of its GPU targets back to the CPU, one at a time, waiting each time. Now it
  only copies what the game reads, in one step, and keeps the GPU fed during the frame (IN-357/IN-358). The flare
  values are byte-identical to before. Headless night race: 20-28 -> 11-19 ms per frame.
- GPU time can now be measured per category (`GT4_HW_GPU_TIMING=1`): about 8-9 ms per night frame, so the remaining
  cost of the heaviest frames is on the CPU (the GS command parser).
- The GS command front end got cheaper (constant-time memory overlap checks, reused buffers, no extra copies of
  texture data). Headless: night race 10-17 ms, day race 15-17 ms per frame, at the 60 FPS line.
- Owner request: tests now start like the real launcher (16:9, races at 480p). The owner's last session had raced
  at 480i because the test script did not pass the launcher's setting; the script now does and prints which video
  mode the race used. At 480p a race frame has about 70% more draw batches: headless 20-21 ms per frame, so that is
  the next target.
- The GS work now runs on its own thread next to the game's CPU emulation, in the same order as before (results
  identical). Headless with the launcher's settings: 480p race 14-15 ms per frame, 480p night race 9-14 ms: under
  the 16.7 ms of 60 FPS. Ready for the owner's next look.
- Owner test 4: smooth 60 FPS on the overlay but small periodic hitches (about 18 ms frames). The window picture of a
  race is now assembled on the graphics card instead of the CPU (identical pixels, checked on every frame of four
  recordings), which takes about 2.5 ms per frame off the busy GS thread.
- The GS stream reader now decodes the most common kind of vertex packet in one fast loop (results checked identical
  on all recordings, plus a new randomised test). The renderer also prints its cost per frame: the GS thread uses about
  11 ms of CPU per 480p race frame (budget 6 ms), so more work on the CPU side is next (CLUT loads, barriers, render
  passes).
- Fewer GPU synchronisation points (about a fifth fewer per frame) and a texture already unpacked earlier in the same
  pass is reused instead of unpacked again: the graphics card does a little less work per frame; the CPU side is
  unchanged. Pictures and memory identical on every recording.
