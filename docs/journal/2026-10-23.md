## TASK-027 CoreGS 2.0: owner test 6 fixes (branch task/027-coregs2, Claude)

- `main` (release 1.2.3) merged into the branch. Conflicts: the `mtvu::Donor` comment (main's TASK-092 text kept) and
  the 2026-10-22 journal (both sides kept).
- Owner test 6 (4x with FXAA on the owner's 3440 x 1440 monitor) failed in two ways. Both are fixed in local slice270:
  - **The race looked 1x although the graphics card did the 4x work.** Every second frame was shown from the 1x copy
    of the picture. The game reuses part of the picture it is about to show as the depth buffer of a small extra
    image, and that threw away the sharp 4x copy just before it was shown. The renderer now keeps a sharp copy of the
    last shown pictures and uses it wherever the game did not change the picture since. A new automatic check looks at
    the shown picture itself: on the race recording, 1x pictures went from 61 of 121 to 1 (the recording's first frame).
  - **Ultrawide stayed squeezed in a 16:9 box.** The game asked for the full-screen picture, but in this renderer the
    request went nowhere. The race now fills the screen at the game's ratio, as with GSdx; menus stay 16:9.
- Game memory and everything the game reads back stay identical to 1x at every scale (checked at 2x, 4x and 6x).
- Graphics card work per race frame (measured on a recording): 1x 6.5 ms, 2x 9.5, 4x 13.3, 6x about 16 ms.

## TASK-027: owner test 7 fixes (Claude)

- Owner test 7 on the previous candidate: the race still looked 1x at 2x and 6x, although the graphics card did the
  work; the ultrawide picture was right.
- Two more causes, both found on the race recording:
  - The game's colour filter (a tone curve it applies to every race frame) is done with tricks that read the picture
    as 8-bit numbers. The renderer did that step at 1x and lost the sharp copy. The sharp copy is now kept and the same
    colour change is applied to it, checked pixel by pixel against the exact 1x result.
  - The final copy of the race picture to the screen buffer read the picture from the 1x memory because the game
    asks for a larger texture (1024 x 512) than the picture (640 x 448). The renderer now looks at the area the copy
    really reads.
- The automatic check now also catches "a 1x picture with a sharp HUD on top": the previous candidate fails it, the
  new one passes (about 69-79% of the picture's pixel blocks now carry finer detail, against about 6% before).
- Game memory stays identical to 1x at 2x, 4x and 6x. New candidate `O:\gt4recomp-scratch\coregs2-candidate-271`.
