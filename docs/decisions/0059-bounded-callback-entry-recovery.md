# 0059 — Keep callback recovery separate from production

Date: 2026-10-13. Status: accepted for the authorized P0/P1 investigation.

## Context

Slice 116 reproduced the baseline EE producer but identified omitted bodies at
`0x0044EA58` and `0x0044EAC8`. Neither baseline equality nor a recovered-function
census establishes complete coverage. The EE dispatcher has no interpreter
fallback for missing targets without a module replacement.

## Decision

Qualify a bounded offline seed experiment before changing production. Use a fresh
verified capsule and the unchanged donor translator. Compare baseline, callback,
supplier and both-seed profiles; require exact addresses, return continuations,
analyzer/registry consistency and wrapper-site deltas. Preserve failed attempts,
generated bytes and receipts under ignored private paths. Publish metadata only.

The supplier-only seed recovers both functions: 45 instructions, nine entries,
18 changed source units, and byte-identical source to both-seeds. All changed
units compile; static ID normalization preserves existing bodies/callers. This
supports a diagnostic recovery contract, not a production pin update.

## Consequences and limits

Production library/runtime/launcher and donor source remain unchanged. Live
reachability, performance relevance, full candidate linking and gameplay are
Unknown/unqualified. P0/P1 remain in progress. Extra incoming r8/r9/r10 dependencies
and transitive callback effects must be preserved before a host render bridge.
Do not duplicate callback evaluation or treat recovered code as proof of a
pure render boundary. No renderer or timing implementation follows from this decision.
